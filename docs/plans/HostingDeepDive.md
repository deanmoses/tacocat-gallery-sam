# Hosting deep dive: Cloudflare vs Bunny.net

Companion to [Hosting.md](Hosting.md). That page states the goals and narrows the field to two vendors; this page records what is actually true on the ground as of 2026-09-22, so the next step can be decided on facts rather than impressions. Three kinds of fact are kept apart below: what was measured from this machine and from the AWS account, what the code requires, and what each vendor's own documentation says today (each vendor claim carries a URL; anything that could not be confirmed against an official page is marked _unverified_).

**Outcome, Oct 2 2026**: Cloudflare. The tests listed under _What would change the decision_ were run against a real account during the port, and their results, with the risks this page raised, are in `docs/Risks.md` of [tacocat-gallery-cloudflare](https://github.com/deanmoses/tacocat-gallery-cloudflare). The DNS move in item 9 happened on 2026-10-02 without incident.

The bill is not compute. It is AWS Backup $6.75 (a weekly S3 backup of the 135 GB originals bucket, 35-day retention), S3 storage $3.52, CloudTrail $0.93, Secrets Manager $0.80. ## What the platform has to replace

Distilled from the code, with the parts that are easy to miss when reading Hosting.md.

- **Read API.** Album (with children and thumbnails, root synthesized, admin sees unpublished), album and media existence checks, latest album, search. No authorizer at the gateway; every Lambda verifies the `id_token` cookie itself and reads report `X-Auth-Status` rather than failing.
- **Write API.** Create, update, delete, rename albums and media; set album thumbnail; recut thumbnail; presigned upload URLs; error lookup. All behind "any valid token from the pool is an admin" (`AuthorizationHelpers.ts`); there is no role check.
- **Derived images.** URL `/i/<path>?version=<v>&size=200x200[&crop=x,y,w,h]` rewritten at the edge to an immutable key; cover-crop of an arbitrary pixel rectangle around a focus point, never upscaled, output format chosen from the source (JPEG stays JPEG, PNG and alpha become WebP, AVIF exists in code but is unreachable through the CDN); quality 85; generated once by Sharp, stored forever in the derived bucket, year-long immutable cache. Any size is accepted and stored. The uploader pre-warms the 1024 detail image through the public CDN.
- **Version keys.** Every derived asset and every image URL carries the S3 `versionId` of the original, which DynamoDB stores. Neither R2 nor Bunny Storage has object versioning, so the new design needs its own immutable per-upload id written into the key. This is a design change either way, not a vendor differentiator; see [Replacing S3 versioning](#replacing-s3-versioning).
- **Crops are pixel rectangles** relative to EXIF-oriented dimensions, stored per media item; the recut API takes percentages and converts.
- **Uploads.** Browser PUTs to a presigned S3 URL; an S3 event triggers a Lambda that extracts IPTC/XMP title, description, keywords and dimensions with ExifReader (pure JS), creates missing year and day albums, upserts the item, and sets the album thumbnail if none. HEIC uploads are converted to JPEG by Sharp with a hand-built libheif layer on x86, then re-processed. Corrupt files are reverted and an error record with a 24 h TTL is written for the UI to show.
- **Video.** MediaConvert produces one progressive H.264 MP4 at source resolution (QVBR 7, 5 Mbps cap, AAC 128k) plus a first-frame JPEG poster; an EventBridge handler moves outputs into place and upserts the item with dimensions and duration. Playback is a byte-range MP4 from the derived bucket. There is no HLS.
- **Search.** RediSearch over RedisJSON on Redis Cloud (`us-east-1`, three databases, configured by hand): TEXT on filename, title, description, summary, tags; TAG on type; NUMERIC sortable date; paged, newest first. Kept in sync by a DynamoDB stream consumer and a manual reconciler. Search is unauthenticated and does not filter unpublished albums.
- **DynamoDB semantics in use.** Conditional puts, `TransactWrite` for publish (checks the parent) and for album rename (album plus every child in one transaction, subject to the 100-item cap), PartiQL updates, `BatchGet`, streams, TTL. All of it maps to SQL transactions trivially; the rename transaction becomes a `BEGIN; UPDATE ...; COMMIT`.
- **Ops.** One JSON log group per stack, an API access log, five CloudWatch alarms to email, a $15 budget alarm, Grafana Cloud synthetic probes from Northern California, Paris and Ohio into Discord, a local DuckDB that ingests CloudFront and CloudWatch logs. CI deploys the test stack per PR and runs 19 integration suites against real AWS resources; push to main deploys staging; prod is a manual dispatch with a release tag.
- **Environments.** Three stacks, three Redis databases, one shared Cognito pool, three custom domains each with `api.`, `img.` and (except test) `auth.` subdomains, ACM certs passed in as parameters.

## Cloudflare, as of 2026-09-22

### Compute and framework

- **Workers Free**: 100,000 requests/day, 10 ms CPU per request, 50 subrequests, 3-day logs. **Workers Paid**: $5/month, 10M requests and 30M CPU-ms included, 30 s CPU default (5 min max), 10,000 subrequests, 7-day logs, and it unlocks Logpush, Containers and Tail Workers (<https://developers.cloudflare.com/workers/platform/pricing/,> <https://developers.cloudflare.com/workers/platform/limits/>). Static asset requests are free and unlimited on both plans. Bundle limit is now 64 MiB uncompressed on both plans (changed 2026-09-04).
- **Node compatibility** is on by default for compatibility dates from 2026-08-04; `fs` is a 128 MB in-memory virtual filesystem. Native addons will "likely never" be supported (workerd maintainer), so Sharp does not run in a Worker, native or WASM (wasm-vips needs threads Workers do not have).
- **SvelteKit**: `@sveltejs/adapter-cloudflare` 7.2.9 (2026-06-16) targets Workers Static Assets and is the official path; the old Workers adapter is deprecated on npm. Cloudflare's own position is "start new projects with Workers" and Pages gets no new investment (<https://blog.cloudflare.com/full-stack-development-on-cloudflare-workers/>). During `vite dev` SvelteKit still runs in Node with emulated bindings, not in workerd; the real Worker is exercised with `wrangler dev` on the build output or the new `createTestHarness()`. SvelteKit 3 / adapter 8 (in `next`) drops Pages and moves to `import { env } from 'cloudflare:workers'`.
- **Cold starts**: no official millisecond figure; the 2020 "under 5 ms, hidden in the TLS handshake" claim applies to Workers on a root hostname, and the 2025 sharding work cut cold-start rate from 0.1% to 0.01% of requests (<https://blog.cloudflare.com/eliminating-cold-starts-2-shard-and-conquer/>). Measured here: 53 to 107 ms TTFB to a sample Worker from Berkeley.
- **Background work**: Queues are on the Free plan since 2026-02-04 (10,000 ops/day, 24 h retention); Cron Triggers (5 per account on Free); Workflows; SQLite-backed Durable Objects on Free. R2 event notifications deliver to a Queue, which a Worker consumes, so the S3-event-to-Lambda upload pipeline maps directly (<https://developers.cloudflare.com/r2/buckets/event-notifications/>).
- **Containers** are GA since 2026-04-13 on Workers Paid, with 375 vCPU-minutes and 25 GiB-hours a month included, 1 to 3 s cold starts, scale to zero after an idle timeout (<https://developers.cloudflare.com/containers/platform/pricing/>). At 300 photos a month a Sharp or ffmpeg container costs nothing above the $5 plan.

### Database

- **D1** is GA (2024-04). Free: 5M rows read/day, 100k rows written/day, 5 GB, 500 MB per database, 50 queries per invocation, 7-day Time Travel. Paid: 25B reads and 50M writes a month included, 10 GB per database, 30-day Time Travel (<https://developers.cloudflare.com/d1/platform/pricing/,> <https://developers.cloudflare.com/d1/platform/limits/>). The gallery's 15 MB and 13k API calls a month are noise against these, but note that since 2026-09-01 the free daily row limits are hard-enforced: queries fail until midnight UTC (<https://developers.cloudflare.com/changelog/post/2026-09-01-d1-free-tier-limit-enforcement/>). A bot storm scanning 5M rows in a day would take the site down on Free; Paid removes the cap.
- **Primary location**: a hint at creation, `wnam` for Berkeley, best effort, not changeable afterwards (<https://developers.cloudflare.com/d1/configuration/data-location/>).
- **Read replication** is still labelled beta in the docs source (no GA entry in the changelog). Replicas in every region including WNAM and WEUR; the Sessions API gives read-your-writes and monotonic reads via a bookmark, and `first-primary` forces the first query to the primary (<https://developers.cloudflare.com/d1/best-practices/read-replication/>). Documented replica lag from a WNAM primary: 30 ms to ENAM, 75 ms to WEUR. Independent production numbers: point reads p50 about 1 ms, p95 2 to 6 ms, single-row writes p50 35 ms (<https://tanstackship.com/blog/cloudflare-d1-performance-for-saas>).
- **Backups**: Time Travel restores in place only; there is no restore-to-a-new-database yet (<https://developers.cloudflare.com/d1/reference/time-travel/>). `wrangler d1 export` writes a SQL file, but refuses any database containing a virtual table, which includes FTS5 (<https://developers.cloudflare.com/d1/best-practices/import-export-data/,> open issue <https://github.com/cloudflare/developer-platform/issues/43>). Cloudflare's suggested workaround is to drop the virtual tables, export and recreate them, which takes search down, and "a running export will block other database requests" in any case. The workaround that costs nothing is to not use the export tool: a cron Worker reads the canonical tables (skipping the FTS table) in a few paged queries and writes them to R2 as JSON or SQL inserts. At 15 MB this is well inside Worker limits and does not block the database. Restore is loading that dump into an empty database and rebuilding the index with `INSERT INTO fts(fts) VALUES('rebuild')`; the index is derived data and never needs backing up. So FTS5 stays in the one database, with Time Travel for fast in-place undo and the R2 dump (copied off-vendor alongside the originals backup) as the real backup. Whether Time Travel restores FTS5 tables correctly is undocumented; it works at the storage level so it should, but test it.
- **FTS5** is supported, with JSON and math functions (<https://developers.cloudflare.com/d1/sql-api/sql-statements/>). Trigger support for keeping the FTS table in sync is undocumented; test it. Without triggers, the API writes the row and its FTS row in the same `batch()`, which D1 runs as one transaction, so the index cannot drift. That atomicity is the reason not to put the index in a second D1 database or in Redis: D1 has no cross-database transactions, triggers or `ATTACH`, and read replication copies one database rather than syncing two, so any separate index needs dual writes and a reconciler, which is the Redis setup today.

### Storage and media

- **R2**: $0.015/GB-month, Class A $4.50/M, Class B $0.36/M, free egress, 10 GB and 1M Class A free (<https://developers.cloudflare.com/r2/pricing/>). Full-enough S3 API: multipart, CopyObject, conditional headers, presigned PUT (S3 endpoint only, not custom domains). No object versioning, no tagging, no bucket policies. Lifecycle rules and event notifications exist. Super Slurper migrates from S3 for free apart from AWS egress (about $12 for 135 GB at AWS's rate). Location hint `wnam`, fixed at creation.
- **Images**: HEIC input is supported on all plans since 2025-07-08 (<https://developers.cloudflare.com/changelog/post/heic-support/>); outputs JPEG, WebP, AVIF, `format=auto`; `fit=cover`, `gravity=XxY` focal point, and `trim.left/top/width/height` for an arbitrary rectangle, so the gallery's crop-then-cover semantics are expressible (<https://developers.cloudflare.com/images/optimization/features/>). Quality default 85. EXIF survives only in JPEG output. Free: 5,000 unique transformations per calendar month, then new ones fail with error 9422; Paid: $0.50 per 1,000 beyond 5,000 (<https://developers.cloudflare.com/images/pricing/>). A unique transformation is one (source, parameters) pair per calendar month, whatever the cache did. The gallery requests about 7,750 distinct variants a month today, so on-demand transformation on the Free plan would break, and on Paid would cost about $1.40 a month. Generating once and storing the result in R2, as the code does today with S3, keeps the count to new photos times variants (a few hundred a month) and stays free. The Images binding in a Worker is billed the same way since 2026-07-01; the tutorial says it needs an Images Paid subscription, which has no stated base fee beyond usage (_unverified_ whether $0 usage means $0).
- **Stream**: $5 per 1,000 minutes stored (prepaid, so $5/month is the floor), $1 per 1,000 minutes delivered, encoding free, H.264 360p to 1080p ladder, HLS and DASH, thumbnails at any timestamp, signed URLs, upload from a URL, webhook on ready (<https://developers.cloudflare.com/stream/pricing/>). Originals are not retained. HEVC input from iPhones is not documented either way (_unverified_). Alternative: ffmpeg in a Container on Workers Paid, which Cloudflare itself demonstrates; then the MP4-only pipeline the gallery has today carries over unchanged and Stream is not needed.

### Domain and DNS

This is the one hard constraint. Custom Domains and Routes both require the hostname's zone to be on Cloudflare; a CNAME from DreamHost to a `workers.dev` hostname fails with error 1001 (<https://developers.cloudflare.com/support/troubleshooting/http-status-codes/cloudflare-1xxx-errors/error-1001/>). Partial (CNAME) setup is Business and above; registering `pix.tacocat.com` as its own zone is Enterprise only (<https://developers.cloudflare.com/dns/zone-setups/partial-setup/,> <https://developers.cloudflare.com/dns/zone-setups/subdomain-setup/>). Two ways through on the Free plan:

1. Move tacocat.com's nameservers from DreamHost to Cloudflare. Cloudflare scans and imports the existing records; the Google MX and the DreamHost-hosted apex site keep working as DNS-only records. The risk is the import missing something in a 30-year-old zone; the mitigation is exporting the DreamHost zone first and diffing. The export has been done; see the next section.
2. Cloudflare for SaaS: put any other domain you own on Cloudflare as a full zone, use a Worker as its fallback origin, and CNAME `pix.tacocat.com` from DreamHost to it. 100 custom hostnames are free (<https://developers.cloudflare.com/cloudflare-for-platforms/cloudflare-for-saas/start/getting-started/>). This works but is a workaround built on a product aimed at SaaS vendors.

Note Pages, unlike Workers, does allow custom domains outside Cloudflare zones, but Pages is the platform Cloudflare has stopped investing in.

### The tacocat.com zone, as exported 2026-09-22

Pulled with the DreamHost API (`dns-list_records`), which also returns the records DreamHost manages itself and the panel does not let you edit; 22 of the 52 are of that kind, and they are the ones a manual copy or Cloudflare's scan is most likely to miss. The registrar is GoDaddy, so the nameserver change is made there, not at DreamHost. The zone is not DNSSEC-signed, so there is no DS record to remove first. There are no wildcard, AAAA or CAA records, and only A, CNAME, MX and TXT types.

| Group                                                                                                                                 | Records | On Cloudflare                                                                                                                                                |
| ------------------------------------------------------------------------------------------------------------------------------------- | ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| ACM certificate validation CNAMEs for every AWS hostname                                                                              | 14      | DNS-only. Removing them stops the AWS certificates renewing.                                                                                                 |
| AWS service CNAMEs: `pix`, `staging-pix`, `img.*`, `api.*`, `auth.*`, `cdn`, `login`                                                  | 12      | DNS-only while they still point at CloudFront or API Gateway; proxying in front of CloudFront stacks two CDNs.                                               |
| Google Workspace: 5 MX, `google._domainkey` DKIM, site verification TXT, 5 `ghs.googlehosted.com` CNAMEs                              | 12      | Copied exactly. See mail below.                                                                                                                              |
| DreamHost hosting A records to `205.196.220.123`: apex, `www`, `ftp`, `ssh`, and `dev-pix`, `prod-pix` with their `www`, `ftp`, `ssh` | 12      | Kept for the apex and `www`. DreamHost updates these itself today; on Cloudflare they are static and go stale if DreamHost moves the site to another server. |
| Leftovers: `gallery3` to `64.90.63.108`, `vercel-pix`                                                                                 | 2       | Probably dropped, with `dev-pix`, `prod-pix` and `ftp`/`ssh`, leaving about 35 records.                                                                      |

The move is therefore small. The one part that cannot fail is mail: all `@tacocat.com` mail is Google Workspace, and only the apex has MX records. If the MX records went missing, senders would fall back to the apex A record and deliver to DreamHost, which bounces rather than defers. The DKIM key is a long 2048-bit TXT value and the record most likely to be damaged in a copy. There is no SPF or DMARC today; adding them is worth doing, but as its own change after the move, not during it.

The procedure that keeps mail safe:

1. Create the zone on Cloudflare. Nothing is live until the nameservers change at GoDaddy.
2. Query every exported record against the two assigned `*.ns.cloudflare.com` servers, which answer before they are delegated, and diff exactly against the export: MX priorities and the DKIM string byte for byte. Switch only on a clean diff.
3. Change the nameservers at GoDaddy. For up to 48 hours resolvers see either DreamHost or Cloudflare, and both answer identically.
4. Leave the DreamHost zone in place for at least a week.
5. Send mail both ways with an outside account, check `DKIM: PASS` in Gmail's "Show original", and check the Google Admin console still shows the domain verified and DKIM authenticating.

Reverting the nameservers also takes up to 48 hours to reach everyone, so step 2 is the safeguard, not rollback.

### Auth, search, ops, IaC, local dev

- **Auth**: Cloudflare Access can protect a single path such as `/admin/*` with Google or GitHub login, and since 2026-08-14 a Worker can read the verified identity with `ctx.access.getIdentity()` and no JWT code (<https://developers.cloudflare.com/workers/configuration/cloudflare-access/>). Zero Trust Free needs a payment card on file even though it is not charged; the "50 free users" figure is on a 2020 blog and third-party pages but not on a current official page (_unverified_). Application-level alternatives: Better Auth 1.5+ has a native D1 dialect; Auth.js has `@auth/d1-adapter` and `@auth/sveltekit`.
- **Search**: D1 FTS5 as above. Vectorize and Workers AI embeddings are free at this size if semantic search is ever wanted. Upstash's new Redis Search uses different commands from RediSearch, so the existing search code is a rewrite in any case.
- **Ops**: Workers Logs free with 3-day retention and a Query Builder; Analytics Engine (`writeDataPoint` per request, SQL API, 90-day retention) is free and unbilled today; Logpush of raw request logs to R2 needs Paid. Any of these feeds DuckDB more simply than the current CloudWatch export.
- **IaC**: Terraform provider v5.25.0 is generated from the OpenAPI spec and has 170 open issues; Cloudflare's own stabilized list covers DNS records, R2, Queues, KV, Workers scripts and routes, Access apps, Logpush, but `d1_database` missed its June 2026 stabilization target and the newer `cloudflare_worker` resources are labelled beta (<https://github.com/cloudflare/terraform-provider-cloudflare/issues/6237>). `wrangler.jsonc` with `env.staging`, `env.test`, `env.prod` covers Workers, bindings, D1, R2, KV, Queues, cron, custom domains and secrets without Terraform, and Wrangler's automatic resource provisioning is in beta. Workers Builds (Git push to deploy, free 3,000 minutes) and the new Worker Previews (per-PR, GA 2026-09-22) cover CI; Terraform cannot connect the Git repo. Alchemy has first-class SvelteKit, Images and Stream resources but is a one-maintainer beta.
- **Local dev**: D1, R2, KV, Queues, Durable Objects, Workflows and Containers all run locally in Miniflare with state under `.wrangler/state`; Images runs locally with width, height, rotate and format only (<https://developers.cloudflare.com/workers/development-testing/bindings-per-env/>). `@cloudflare/vitest-plugin` (renamed 2026-08-19, Vitest 4.1 only, not yet Vitest 5) runs tests inside workerd with per-file isolated storage and `applyD1Migrations`. Any binding can be flipped to the real remote resource with `remote: true`.

### Business

Q2 2026 revenue $696M, up 36%, free cash flow positive, $4.2B cash against $3.3B convertible notes, one 1,100-person restructuring in May 2026 (<https://www.sec.gov/Archives/edgar/data/1477333/000147733326000053/q226exhibit991.htm>). ## Bunny.net, as of 2026-09-22

### Compute and framework

- **Edge Scripting**: Deno-based (last stated version 2.1.5 in March 2025; current version _unverified_), `npm:` and `jsr:` imports, `node:fs` as a 64 MB in-memory VFS, WASM, WebSockets, a Cache API since 2026-09-10. Limits: 30 s CPU per request, 128 MB, 50 subrequests, 10 MB script, 500 ms startup (<https://bunny.net/docs/scripting/limits>). Price $0.20 per million requests plus $0.02 per 1,000 CPU-seconds, no free tier, $0.22 floor (<https://bunny.net/docs/scripting/pricing>). Two modes: standalone (the script is the origin, gets a `*.bunny.run` host and custom domains with free certs) and middleware on a pull zone with hooks before cache, on origin request and response, and on client response (<https://bunny.net/docs/scripting/middleware/overview>). `waitUntil` exists for work after the response.
- **No scheduled or cron triggers** anywhere in the docs, API or Terraform provider. **No key-value store**; the Cache API is per-region and not replicated.
- **Cold start**: vendor claims "as close as possible to 0 ms" and "a large portion under 15 ms" (<https://bunny.net/blog/edge-scripting-just-evolved-faster-safer-and-even-more-powerful/>); no independent measurement found, and no public script hostname was found to measure from here.
- **SvelteKit**: Bunny's official adapters repo (created 2026-08-19) has an Astro adapter marked "lab, do not run in production" and lists the SvelteKit adapter as Planned (<https://github.com/BunnyWay/bunny-adapters>). One community adapter exists on GitHub only, six stars. SSR on Bunny today means writing the adapter or running Node in a Magic Container, which has no scale-to-zero and costs about $16 a month for one small always-on instance (<https://bunny.net/docs/magic-containers/pricing>). The static SPA the gallery ships today works unchanged: files in a storage zone behind a pull zone.
- **Local dev**: the SDK runs a script under Node or Deno locally; the CLI (public preview) has no `dev` command and does not build. Storage, database and pull-zone behaviour are the real network.

### Database

- **Bunny Database** is in public preview since 2026-02-03, free during preview, then $0.30 per billion rows read, $0.30 per million rows written, $0.10/GB per active region (<https://bunny.net/database/>). Bunny's own fork of libSQL. Limits: 50 databases, **1 GB per database** (raisable on request) (<https://bunny.net/docs/database/limits>). The gallery is 15 MB.
- **Placement**: at-rest storage in Toronto or Frankfurt only (the dashboard shows it as "North America" or "Europe"); primaries and replicas run in 41 edge compute regions, of which 12 are in North America including San Jose, Los Angeles and Seattle. The dashboard's manual mode lets any of those be marked as a primary candidate, and the same screen states that "only one is active at a time" and "the active primary region is selected automatically based on latency", so this is a single-writer database with a floating primary, not multi-master. The practical setting for this gallery is San Jose and Los Angeles as the only primary candidates, so the active primary can never land on the East Coast, with replication enabled in every region readers use, Paris and Marseille included. Replicas proxy writes to the primary; "read-your-writes consistency is not guaranteed when reading from replicas" and there is no documented flag to force a primary read (<https://bunny.net/docs/database/durability-and-consistency>). The failover data-loss window is 10 seconds or 4,096 WAL frames.
- **Idle eviction and cold starts**: the creation screen states "When a database is idle, we move it to object storage and remove it from active regions to reduce costs", and that "if a database becomes idle, the active primary region may change when it is reactivated." Replicas are "dynamically provisioned" as well. Reactivation therefore means pulling the snapshot and WAL from Toronto into a compute region before the first query answers, and a Paris replica woken by a French reader pulls across the Atlantic. Neither the idle threshold nor the reactivation time is published. At this site's traffic, where quiet hours see one to three requests, idle is the normal state, so most visits after a lull would pay it. This is the same shape as the Lambda cold start the plan is trying to escape, with an unknown number attached. D1 documents no eviction to object storage; a Durable Object's isolate is evicted when idle but its SQLite file stays on local disk in the colo. Two mitigations exist on Bunny: keep the database off the read path by materializing album JSON into Storage (see the architecture sketch below), and keep it warm with an external ping, since Bunny has no cron; the existing Grafana Cloud probes already hit the site every ten minutes from Northern California, Paris and Ohio, which would keep a primary and two replicas warm for free if the idle threshold is longer than that.
- **Backups**: none exposed. "Automatic backups" and "import/export" were listed as upcoming at launch and have not appeared in the changelog. The only user-facing export is `.dump` from the database shell. A hidden management API has preview `list_versions`, `restore` and `fork` endpoints, not in the public docs (<https://api.bunny.net/database/docs/private/api.json>). A major "Database Controller Outage" is on the status history for 2026-08-25.
- **Access**: standard libSQL Hrana over HTTP on a public hostname, so it works from localhost and from CI; tokens are minted in the dashboard or the CLI, not by the public API and not by Terraform (<https://bunny.net/docs/database/connect/authorization>). **FTS5 on Bunny's fork is not mentioned anywhere** (_unverified_; upstream libSQL builds it by default).

### Storage and media

- **Bunny Storage**: $0.01/GB per region on the Standard tier, Los Angeles is a Standard region, a second replica region doubles the storage price (<https://bunny.net/pricing/storage/>). S3-compatible API in public preview with presigned URLs, multipart, CopyObject, conditional requests; **no versioning, no lifecycle, no tagging** (<https://bunny.net/docs/storage/s3>). **No event notifications or webhooks of any kind on object writes**, so the upload-triggers-processing pipeline has to become "client uploads, then calls the API to finalize" or "uploads go through an Edge Script". Presigned PUT from a browser is documented for GET only (_unverified_ for PUT). No first-party migration tool from S3; rclone through the S3 endpoint is the documented path.
- **Bunny Optimizer**: $9.50 per pull zone per month, unlimited transformations, hourly billed (<https://bunny.net/docs/optimizer/pricing>). HEIC, HEIF and AVIF input since 2026-06-26; outputs JPEG, PNG, WebP, GIF, AVIF; `crop=w,h,x,y` for an arbitrary rectangle, `focus_crop`, `crop_gravity`, `aspect_ratio`, `width`, `height`, `quality` (default 85), `format`, and named Image Classes (<https://bunny.net/docs/optimizer/dynamic-images/cropping>). Automatic format negotiation is WebP only; AVIF must be explicit and is capped at 4 MP output. Variants are generated on cache miss and cached at the edge; there is no stored derived copy and no charge for regeneration. Because it is per pull zone, three environments cost $28.50 unless staging and test share prod's image zone via per-hostname edge rules, or go without Optimizer.
- **Bunny Stream**: storage $0.01/GB (every rendition, MP4 fallback and kept original counts), standard encoding free, delivery at CDN rates, no per-video fee (<https://bunny.net/docs/stream/pricing>). HLS plus opt-in MP4 fallback at 240p to 1080p, H.264 or H.265 or AV1, thumbnails, previews, TUS uploads, fetch from URL, webhook on ready, token-authenticated playback without paying for DRM. For 52 videos this is pennies.

### Domain, CDN, DNS

- A plain CNAME from DreamHost to `<zone>.b-cdn.net` and a free auto-renewing certificate; Bunny DNS is optional and only needed for apex flattening and wildcard certs (<https://bunny.net/docs/cdn/custom-hostname>). No DNS move required.
- CDN $0.01/GB in Europe and North America, no request fees, $1 account-wide monthly minimum. 50 edge rules per zone with per-path origin switching, so one pull zone can serve `/` from a storage zone, `/api/*` from a script and `/i/*` from another storage zone. Token authentication, geo-blocking, and Bunny Shield Basic (WAF, two rate-limit rules, AI-scraper bot categories) are free (<https://bunny.net/docs/shield/verified-bots>).

### Auth, search, ops, IaC

- **Auth**: no identity product; the script implements OAuth itself (Google OIDC is a few hundred lines) and stores sessions in the database. No published Auth.js or Better Auth integration for Edge Scripting.
- **Search**: no search product. Options are FTS5 in Bunny Database (if it exists), Turso Cloud's free tier (5 GB, FTS5, backups on paid plans, and the upstream of Bunny's engine), or Redis Cloud and Upstash as today.
- **Ops**: request logs for 3 days via API, Permanent Log Storage into a storage zone you own (gzip files, ideal for the DuckDB pipeline), syslog and Datadog forwarding. **No alerting of any kind** beyond billing emails: no error-rate, origin-down or spend alerts, and DNS health checks send nothing (<https://bunny.net/docs/shield/metrics>). The five CloudWatch alarms would have to be replaced by external monitoring; the Grafana Cloud probes already cover uptime. Edge Scripting log retention is undocumented.
- **IaC**: Terraform provider v0.19.0 (2026-09-22) covers pull zones, hostnames with auto certs, edge rules, storage zones, scripts with variables and secrets, DNS, Stream libraries, Shield, containers, Optimizer classes and the database itself, but not database tokens (<https://github.com/BunnyWay/terraform-provider-bunnynet>). A September 2026 issue reports database creation failing with a hard-coded region. Dashboard-only: account, API keys, database tokens, GitHub linking.

## Replacing S3 versioning

Neither R2 nor Bunny Storage has object versioning, but the gallery uses it for three distinct jobs, and none of them needs a versioned bucket:

1. **Cache-busting ID.** DynamoDB stores the original's S3 `versionId`, which appears in every derived key (`i/<path>/<versionId>/200x200`) and every CDN URL, so derived assets can be cached immutably for a year.
2. **Rolling back a failed replacement.** When a file dragged over an existing one fails processing, `revertS3Version` deletes the new version so the previous one becomes current again.
3. **Recovery.** Overwritten and deleted originals stay recoverable for 24 days through the noncurrent-version expiry.

The replacement is to never overwrite an original. Originals live at immutable keys and the database says which one is current:

```text
originals/2024/06-15/photo.jpg/<versionId>      ← written once, never overwritten
i/2024/06-15/photo.jpg/<versionId>/200x200      ← derived keys unchanged
```

- **The server mints `versionId`** when it issues the presigned PUT. A ULID is opaque, URL-safe and sortable. The field keeps its name, so the item schema, the search index, the front end and the URL format are untouched. A content hash buys deduplication the gallery doesn't need and costs hashing large videos in a Worker.
- **Rollback becomes not committing.** Processing reads the new object and only on success updates the item's `versionId`, conditional on the new ID sorting after the current one so out-of-order completions can't regress it. On failure it records the error and deletes the new object. The current original is never touched, which also closes today's window where the site briefly points at the broken upload.
- **Recovery becomes a purge job.** Originals that are no longer current, whether replaced or soft-deleted in the database, are removed by a scheduled job after 30 days. R2 lifecycle rules filter only by prefix and age and can't tell current from superseded, so the job has to consult the database. Restoring is pointing `versionId` back at the old key. On Bunny, which has no scheduled jobs, this runs from GitHub Actions.
- **Backup stays separate.** Soft delete protects against app bugs, not against losing the account or the bucket; the external copy above is still required.
- **Migration keeps every URL valid.** Each current original is copied to `originals/<path>/<its existing S3 versionId>`. The existing IDs are just opaque strings, so derived keys, cached URLs and database rows all carry over, and the derived bucket copies as-is.
- **Rename gets simpler.** `renameMedia` gets a new `versionId` today because S3's copy mints one; with self-minted IDs it keeps the old one. Derived assets still move, or regenerate on demand, because the path is in the key.
- **Upload trigger.** R2 event notifications feed a Queue consumer, the same shape as S3 to Lambda. Bunny has no storage events, so the client calls a finalize endpoint after its PUT. The key scheme is identical on both, so versioning is not a vendor differentiator.
- **The cost is dropping files straight into the bucket.** Keys no longer equal gallery paths, so placing a file at `YYYY/MM-DD/name.jpg` no longer publishes it. If that still matters for dev and test, an `inbox/` prefix whose event handler moves files to `originals/<path>/<new id>` preserves it on R2.

## Two architectures, sketched

**Cloudflare.** One Worker per environment serving the SvelteKit app (SSR or the current SPA), `/api/*` routes in the same Worker, D1 with a `wnam` primary and read replication via the Sessions API, R2 for originals and stored derived images with a `wnam` hint, R2 event notifications into a Queue whose consumer extracts EXIF and upserts, the Images binding to generate variants (HEIC in, JPEG or AVIF out, crop plus focal cover) which are written to R2 on first request, Stream or a Container for video, Access on `/admin/*` for the four of you with Google login, FTS5 in the same D1 kept in sync by trigger or `batch()`, a cron Worker that dumps the D1 tables to R2 nightly, Analytics Engine for per-request telemetry. All of it declared in one `wrangler.jsonc` with three environments; a GitHub Action or Workers Builds deploys. Local development and tests run entirely offline in Miniflare. The price is moving tacocat.com's nameservers.

**Bunny.** A pull zone per environment with `pix.tacocat.com` CNAMEd from DreamHost, static SPA files and album JSON materialized into a storage zone (LA, optionally plus Frankfurt), `/api/*` routed by edge rule to a standalone Edge Script that reads and writes Bunny Database (or Turso), the browser uploading through the script or via S3 presigned PUT then calling a finalize endpoint that reads EXIF, Optimizer on the image zone doing HEIC, crop and resize on the fly from the originals, Stream for video, Shield Basic for bots, Permanent Log Storage feeding DuckDB, `.dump` in CI as the database backup. Terraform declares nearly all of it. Reads never touch compute if album JSON is materialized, which is the fastest possible shape for this traffic. The price is a preview database with no backups, no scheduled jobs, no storage events, and building the SvelteKit adapter and the auth yourself.

## What would change the decision

Things that are cheap to test with a trial account and that the documentation does not settle:

1. **Bunny Database FTS5.** `CREATE VIRTUAL TABLE t USING fts5(a)` on a preview database. If it fails, search needs a third vendor.
2. **Bunny Database idle latency.** Create a preview database with San Jose and Los Angeles as the only primary candidates and Paris as a replica, leave it idle for one, six and twenty-four hours, and time the first query each time from Berkeley and, via the Grafana probe, from Paris. This also reveals the idle threshold, which decides whether the ten-minute probes can keep it warm.
3. **Bunny read-your-writes.** Write, then immediately read from a script in Paris or Marseille; measure the lag. The admin's post-save re-read depends on this.
4. **Bunny presigned PUT from a browser** against the S3 preview endpoint, with the fixed `*` CORS.
5. **Bunny Edge Script TTFB from Paris and New Orleans**, via the existing Grafana Cloud probes pointed at a hello-world script. No independent number exists.
6. **Cloudflare D1 replica read latency from Paris** on a `wnam` primary with the Sessions API, same probes.
7. **Cloudflare Images crop semantics**: confirm `trim.left/top/width/height` plus `fit=cover` with `gravity` reproduces the current focus-crop output on a few known images.
8. **Cloudflare Images binding on $0 usage**: whether the required Images Paid subscription bills anything at zero usage.
9. ~~**DreamHost zone export** for tacocat.com, to see how big the DNS move really is.~~ Done 2026-09-22: 52 records, about 35 after dropping leftovers, nothing exotic; see [the zone section](#the-tacocatcom-zone-as-exported-2026-09-22).
10. **Cloudflare D1 with FTS5**: whether triggers keep an FTS5 table in sync, and whether a Time Travel restore brings the FTS5 table back consistent with the canonical tables.

## Where this leaves the decision

On the requirements as written, Cloudflare meets more of them today. The ones Bunny misses are not cosmetic: database backups are a stated requirement and Bunny has none; the database is a preview with a 1 GB cap, a major outage last month, and an idle-eviction design whose cold-start cost is unpublished; there are no scheduled jobs and no storage events, so two of the gallery's three background pipelines have to be re-shaped around the client; SvelteKit SSR needs an adapter that is "Planned"; and there is no alerting. Bunny wins cleanly on the domain (no DNS move), on media pricing simplicity, on pay-as-you-go, and on the log pipeline, and it ties on edge latency from here.

The honest framing is that Bunny is a fine CDN, storage and media company whose compute and database products are twelve to twenty months behind Cloudflare's for this workload, and that Cloudflare's one real cost is the nameserver move. The zone export in item 9 shows that move is small, with Google mail the one part needing care, so the case for Bunny rests on preference rather than requirements. If the preference is strong, the way to hold it is to build on Bunny with Turso as the database (backups, FTS5, PITR on the paid plan, the same libSQL wire protocol Bunny speaks) and accept a third vendor and hand-written auth, and to run items 1 to 5 first, item 2 above all, since an unmitigated database cold start would defeat the sub-100 ms goal on its own. Either path keeps the media pipeline shape the code has today; the version-id scheme changes on both, in the same way (see [Replacing S3 versioning](#replacing-s3-versioning)).
